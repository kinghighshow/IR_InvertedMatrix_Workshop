De-fanging dangerous triggers in GitHub Actions across an organization

<h3 style="text-align: left;"><span style="font-size: 11pt; white-space: pre-wrap;">Authors: Mike Fiedler, Seth Larson</span></h3><span id="docs-internal-guid-ef9de01e-7fff-03f1-aef6-ce4e4d25aad1"><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">On December 2, 2026, GitHub will</span><a href="https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2/" style="text-decoration: none;"><span face="Arial, sans-serif" style="color: black; font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> </span><span face="Arial, sans-serif" style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">start blocking the </span><span>pull_request_target</span><span face="Arial, sans-serif" style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;"> trigger by default</span></a><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> in public repositories. If that sentence means nothing to you, this post is for you. If it fills you with dread, it is also for you.</span></p><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">The short version: a handful of GitHub Actions triggers let a stranger on the internet start a workflow that may have access to your secrets. On a GitHub Team or Enterprise plan, you can turn them off for every repository in your organization with one policy. On a Free plan, you can do it one repository at a time. Set the policy up, check what it would block, then enforce it.</span></p><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">Mike Fiedler, PyPI Safety and Security Engineer, and Seth Larson, Security Developer in Residence, have removed dangerous triggers and applied these policies to the Python Software Foundation (PSF) stewarded GitHub organizations (</span><a href="https://github.com/psf" style="text-decoration: none;"><span face="Arial, sans-serif" style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">psf</span></a><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">, </span><a href="https://github.com/python" style="text-decoration: none;"><span face="Arial, sans-serif" style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">python</span></a><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">, </span><a href="https://github.com/pypi" style="text-decoration: none;"><span face="Arial, sans-serif" style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">pypi</span></a><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">). They also wrote up <a href="https://alpha-omega.dev/blog/de-fanging-dangerous-triggers-in-github-actions-across-an-organization/" rel="nofollow" target="_blank">technical documentation</a> on how to roll these policies out to your own projects and organizations. The full details and technical documentation are available on <a href="https://alpha-omega.dev/blog/de-fanging-dangerous-triggers-in-github-actions-across-an-organization/" rel="nofollow" target="_blank">the Alpha-Omega blog</a>.</span></p><div><span face="Arial, sans-serif" style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"><span id="docs-internal-guid-668ee174-7fff-74ee-6666-39ef97454fa9"><h2 style="line-height: 1.38; margin-bottom: 4pt; margin-top: 18pt; text-align: left;"><span style="font-size: 17pt; font-variant: normal; vertical-align: baseline;">Have dangerous triggers caused real incidents?</span></h2><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;">Yes, repeatedly. A few that have affected projects hosted on PyPI directly:</span></p><ul style="margin-bottom: 0px; margin-top: 0px; padding-inline-start: 48px; text-align: left;"><li style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre;"><p style="line-height: 1.38; margin-bottom: 0pt; margin-top: 12pt;"><a href="https://blog.pypi.org/posts/2024-12-11-ultralytics-attack-analysis/" style="text-decoration: none;"><span style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">Ultralytics, December 2024</span></a><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">. The project's GitHub Actions workflows were compromised and the build cache was poisoned, which put malicious releases on PyPI. Seth wrote PyPI's analysis.</span><a href="https://blog.yossarian.net/2024/12/06/zizmor-ultralytics-injection" style="text-decoration: none;"><span style="color: black; font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> </span><span style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">William Woodruff's write-up</span></a><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> traces the entry point to a </span><span>pull_request_target</span><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> workflow.</span></p></li><li style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre;"><p style="line-height: 1.38; margin-bottom: 0pt; margin-top: 0pt;"><a href="https://blog.pypi.org/posts/2026-04-02-incident-report-litellm-telnyx-supply-chain-attack/" style="text-decoration: none;"><span style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">LiteLLM and Telnyx, March 2026</span></a><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">. Malicious releases of both packages were published after an API token was exposed through an exploited Trivy dependency.</span><a href="https://www.stepsecurity.io/blog/trivy-compromised-a-second-time---malicious-v0-69-4-release" style="text-decoration: none;"><span style="color: black; font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> </span><span style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">StepSecurity traced</span></a><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> the Trivy compromise back to a </span><span>pull_request_target</span><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;"> workflow exploited three weeks earlier. We worked with both maintainer teams on token rotation, release removals, and moving to Trusted Publishers, which both projects have since adopted.</span></p></li><li style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre;"><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 0pt;"><a href="https://labs.cloudsecurityalliance.org/research/csa-research-note-pypi-elementarydata-supply-chain-20260429/" style="text-decoration: none;"><span style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline; white-space: pre-wrap;">elementary-data, April 2026</span></a><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline; white-space: pre-wrap;">. A workflow triggered by comments puts the comment text straight into a shell script. One crafted comment on a pull request ran with a token that could be written to the repository. The attacker used it to commit a malicious file and push a release tag, and the project's own release pipeline published the result to PyPI.</span></p></li></ul><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;">The maintainers behind these projects weren't careless. These triggers look harmless in a workflow file, and the unsafe version is one line away from the safe one.</span></p><div style="text-align: left;"><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"><span id="docs-internal-guid-f2358dda-7fff-a93c-d2d0-ebaa7a7b9606"><h2 style="line-height: 1.38; margin-bottom: 4pt; margin-top: 18pt; text-align: left;"><span style="font-size: 17pt; font-variant: normal; vertical-align: baseline;">Why are these triggers dangerous?</span></h2><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;">Insecure triggers can run workflows with access to your secrets, and a stranger can start them.</span></p><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;">When someone opens a pull request from a fork, the </span><span>pull_request</span><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"> trigger runs their code with a read-only token and no secrets. That's the safe one.</span></p><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span>pull_request_target</span><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"> looks </span><span style="font-size: 11pt; font-style: italic; font-variant: normal; vertical-align: baseline;">almost the same</span><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"> in a workflow file and behaves very differently. It runs with a read/write token and access to your repository and organization secrets. GitHub built it for chores like labeling pull requests from forks, where the workflow never touches the contributor's code. Their code now runs with your credentials. This is called a "pwn request", and </span><a href="https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/" style="font-size: 11pt; text-decoration: none;"><span style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline;">GitHub's docs</span></a><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"> describe it as the root cause of multiple supply-chain compromises.</span></p><p style="line-height: 1.38; margin-bottom: 12pt; margin-top: 12pt; text-align: left;"><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;">The </span><span>issue_comment</span><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"> trigger carries the same risk. This trigger fires when anyone comments on an issue or pull request, and the workflow runs with the repository's token and secrets. Sometimes the victim is a "comment </span><span>/test</span><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"> to run CI" bot that checks out the pull request and runs their code. Sometimes the workflow pastes the comment text into a templated shell command, and the comment turns out to inject different instructions into the workflow shell.</span></p><div style="text-align: left;"><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"><span id="docs-internal-guid-6a2b362f-7fff-ae37-ad5f-3b9e068533b9"><p style="line-height: 1.38; margin-bottom: 4pt; margin-top: 16pt; text-align: left;"></p><h3 style="text-align: left;"><span style="font-size: 17pt; font-variant: normal; vertical-align: baseline;">How did Alpha-Omega support this work?</span></h3><a href="https://alpha-omega.dev/" style="font-size: 11pt; text-decoration: none;"><span style="color: #1155cc; font-size: 11pt; font-variant: normal; text-decoration: underline; vertical-align: baseline;">Alpha-Omega</span></a><span style="font-size: 11pt; font-variant: normal; vertical-align: baseline;"> is a fund and catalyst for sustainable open source security improvements.
